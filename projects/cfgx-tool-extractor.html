OVERVIEW

Config extraction uses the same basic steps for every malware family: run YARA, find the right data, read the bytes, decode or decrypt them, build the config, and save the result. The part that changes is the malware-family code.

cfgx handles all the common work. You only write the part that is specific to the malware family you're analysing.

For each malware family, cfgx expects two family-specific inputs:
1) a YARA rule that identifies the family and points to the config data.
2) a Python family extractor that reads, processes, decodes, or decrypts the matched config data.

The framework's core design principle is: cfgx provides evidence and controlled access to the sample. The family extractor decides what the matches mean and what bytes to process. The framework never knows whether $Config means a configuration blob, a C2 address, or something else entirely — that interpretation lives completely in your extractor.

This separation means you can reuse the same cfgx installation for VoidStealer, RedLine, Lumma, StealC, Qardar, or any future family by simply changing the YARA rule and the family extractor. The framework itself never needs to change.

// THE CORE PRINCIPLE

The framework provides evidence. It knows that rule VoidStealer matched string $steamid at file offset 450664, that the offset falls in the .rdata section at RVA 456992, and that 16 bytes at that location read as b"7656119987836894".

The family extractor decides what that means. Only the extractor knows that $steamid is a Steam ID, that those 16 bytes should be decoded as ASCII, and that the resulting string is a C2 identifier. cfgx never makes those decisions.

DESIGN PHILOSOPHY

Most config tools either contain code for one malware family or try to guess how every sample is encoded. cfgx keeps the two parts separate: cfgx handles the common work, and the family extractor handles the malware-family work.

cfgx is not tied to one malware family. It does not guess what a YARA match means, does not try every decryption method, and does not force one config format. The family extractor makes those decisions.

The algorithm library works the same way. cfgx provides Base64, RC4, AES, XOR, and the other algorithms. The family extractor decides which one the malware uses, which key or IV is needed, and the order of the steps.

This means you can add a new family without changing cfgx. The family extractor is just a Python file with one function. cfgx does the rest.

INSTALLATION & USAGE

Clone the repo and install in editable mode. Editable install registers the cfgx command in your Python environment so you can call it from anywhere. Python 3.12+ needed.

$ git clone https://github.com/SalahEldinFikri/cfgx-tool.git
$ cd cfgx-tool
$ py -3.12 -m pip install -e .
$ cfgx --help

BATCH / FOLDER ANALYSIS

When the sample argument is a directory, cfgx processes every file inside it separately through the full extraction pipeline. Results from all samples are combined into a single JSON report named after the YARA rule. This means you can run cfgx against an entire malware sample collection and get one structured report per family.

DIRECTORY STRUCTURE → COMBINED OUTPUT# Input test_samples/ ├── sample_a ← 10 YARA matches, 3 config values extracted ├── sample_b ← 5 YARA matches, 1 config value extracted └── sample_c ← 8 YARA matches, 2 config values extracted # cfgx processes each separately, then combines cfgx rules/voidstealer.yar test_samples/ extractors/voidstealer.py # Output — one file named after the rule output/ └── voidstealer.json
COMBINED JSON STRUCTURE[ { "sample": "sample_a", "result": { "status": "success", "config": [...] } }, { "sample": "sample_b", "result": { "status": "success", "config": [...] } } ]
// WHY COMBINE INTO ONE FILE

Multiple samples of the same malware family share the same YARA rule. Combining their results into one report lets you compare extracted configurations across samples — useful for tracking C2 evolution, key rotation, or configuration changes between versions of the same family.

EXTRACTION PIPELINE

Every sample, whether a single file or one item in a batch, passes through the same 10-step pipeline. Steps 1–7 and 9–10 are handled entirely by cfgx. Step 8 is yours — it is the only step that contains malware-family logic.

01
CLI Validation Verify all three needed paths exist and are the correct types — rule must be a file, sample can be a file or directory, extractor must be a .py file
02
Load Family Extractor Dynamically import the Python extractor file and verify it has a callable extract(matches, reader) function — fail early with a clear error if not
03
Load PE / ELF Parse the sample binary — identifies format (PE vs ELF), loads sections, image base, and entry point for subsequent offset resolution
04
YARA Scan Compile the rule and scan the sample — produces one result event per string occurrence, not per rule. If $steamid appears 3 times, you get 3 separate events
05
Normalize Matches Convert raw YARA objects into generic { rule, identifier, offset } dicts — a stable interface the extractor can rely on regardless of YARA version
06
Resolve PE Metadata Enrich each match: file offset → PE section → RVA → VA. Adds section, rva, va fields. These let your extractor cross-reference addresses with IDA or a debugger
07
Create SampleReader Wrap the sample file handle in a validated reader — reader.read(offset, size) is the only way the extractor can access sample bytes. No raw file handles, no path exposure
08
extractor.extract(matches, reader) Your code runs here. Select the matches that matter, read bytes at their offsets, decrypt or decode the data using cfgx algorithms, build and return a structured config object
09
Validate Extractor Result Verify the returned dict contains status (must be a string) and config (any value). Reject malformed results with descriptive errors before any output is written
10
Output Print extraction status and config to terminal, write rule-name.json to the output directory. In batch mode, wait for all samples to finish then write the combined report

YARA PROCESSING

YARA processing lives in yara_handler/runner.py. The runner compiles the YARA rule, scans the sample file, iterates through every match and every string instance within each match, and converts them into a flat list of normalized Match objects.

The key design decision is that each string occurrence becomes its own independent Match object. If your YARA rule matches $steamid three times in the same sample (at different offsets), you receive three Match objects — not one match with three occurrences. This is intentional because the family extractor typically needs to process each offset separately.

NORMALIZED MATCH STRUCTURE{ "rule": "VoidStealer", ← YARA rule name "identifier": "$steamid", ← which string matched "offset": 450664, ← raw file offset of this occurrence ← PE metadata added by step 06: "section": ".rdata", ← which PE section contains this offset "rva": 456992, ← relative virtual address "va": 5369166112 ← full virtual address (ImageBase + RVA) } # Multiple occurrences = multiple independent match objects $steamid at 450664 → Match object #1 $steamid at 450688 → Match object #2 $steamid at 450712 → Match object #3
// MATCHES AS ANCHORS, NOT DATA

cfgx treats YARA matches as evidence anchors — they tell you where something interesting is, not what it means. A match says "at offset 450664 there is a pattern that matches $steamid". It does not say "the Steam ID is the 16 bytes starting at that offset". That interpretation is the family extractor's job.

This is why cfgx does not by itself read bytes at match offsets. The extractor calls reader.read(match["offset"], size) explicitly, choosing its own size, direction (before or after the match), and interpretation.

PE & ELF PROCESSING

PE functionality is in formats/pe.py. The module handles loading, section identification, and all address resolution. ELF support mirrors this for Linux/IoT samples.

The most important function is resolve_offset(), which takes a raw file offset (the kind YARA reports) and returns the full address context — section name, RVA, and virtual address. This is by itself applied to every YARA match before the extractor receives them.

ADDRESS RESOLUTION CHAINfile offset (YARA reports this) ↓ PE section lookup ↓ section_start_offset + (offset - raw_data_offset) RVA = section.VirtualAddress + delta ↓ VA = ImageBase + RVA # Example: file offset 452384 section .rdata RVA 456992 VA 5369166112 ← matches address in IDA / x64dbg
AVAILABLE PE FUNCTIONS
FUNCTION PURPOSE
load_pe(path) Load sample as a pefile.PE object — checks the MZ/PE signature, parses headers and sections
get_section_for_offset(pe, offset) Returns the PE section object whose raw data range contains the given file offset — or None if the offset is in the header or overlay
offset_to_rva(pe, offset) Converts a raw file offset into an RVA. Accounts for section alignment and file-to-virtual-address mapping
rva_to_va(pe, rva) Adds ImageBase to an RVA to produce the full virtual address — matches what you see in IDA or a debugger
resolve_offset(pe, offset) One-call convenience: returns { "section": ".rdata", "rva": 456992, "va": 5369166112 } for a file offset
ELF SUPPORT

ELF support in formats/elf.py provides the same capability for Linux and IoT malware: loading, section identification, virtual address resolution, and file-offset-to-virtual-address conversion. The same Match structure is used for both PE and ELF samples — the extractor sees the same interface regardless of binary format.

SAMPLEREADER

cfgx/reader.py provides the SampleReader class — the only way an analyst extractor can access sample bytes. The extractor never receives the sample file path or a raw file handle. All access goes through one method: reader.read(offset, size).

This design keeps access controlled and auditable. The framework knows exactly which bytes the extractor requested and in what order. It also means the extractor cannot accidentally overwrite the sample, seek past the end, or hold an open file handle.

SAMPLEREADER API# The only public method your extractor should call data = reader.read(offset=450664, size=16) # Returns: b"7656119987836894" (raw bytes) # Interpret however the malware requires steam_id = data.decode("ascii") # "7656119987836894" value_le = int.from_bytes(data, "little") # treat as little-endian int # Multiple reads are independent c2_addr = reader.read(match_c2["offset"], 64) port = reader.read(match_port["offset"], 2) key = reader.read(match_key["offset"], 32)
VALIDATION BEHAVIOUR
INPUT RESULT REASON
Normal read Returns bytes Returns exactly size bytes from offset
Negative offset ValueError "Offset cannot be negative" — file positions start at 0
Negative size ValueError "Size cannot be negative" — zero-byte reads return b""
Partial EOF Partial bytes If fewer bytes remain than requested, returns what's available — check len(data)
Offset past EOF b"" Returns empty bytes — the extractor should handle this gracefully
WRITING A FAMILY EXTRACTOR

A family extractor is a simple Python file with one function: extract(matches, reader). You can put the file anywhere and pass its path to cfgx. If you use cfgx algorithms, you can import only the ones you need.

The family extractor receives the YARA matches and a SampleReader. It chooses which matches matter, reads the bytes it needs, processes or decrypts them, and returns status and config.

MINIMAL EXTRACTOR — READS PLAIN ASCII VALUEdef extract(matches, reader): results = [] for match in matches: # 1. Filter — only process the YARA string we care about if match["identifier"] != "$steamid": continue # 2. Read — cfgx gives us the file offset, we choose the size data = reader.read(match["offset"], 16) # 3. Interpret — only the analyst knows what these bytes mean results.append({ "identifier": match["identifier"], "offset": match["offset"], "section": match.get("section"), ← ".rdata", ".data" etc "rva": match.get("rva"), "value": data.decode("ascii"), }) # 4. Return the contract — status (str) + config (anything) return {"status": "success", "config": results}
REALISTIC EXTRACTOR — BASE64 → RC4 DECRYPTION CHAINfrom cfgx.algorithms.base64 import decode as b64 from cfgx.algorithms.rc4 import rc4 import struct def extract(matches, reader): config_match = None key_match = None # Collect the exact strings we need for m in matches: if m["identifier"] == "$config_blob": config_match = m if m["identifier"] == "$rc4_key": key_match = m if not config_match or not key_match: return {"status": "not_found", "config": {}} # Read raw bytes from the sample raw_config = reader.read(config_match["offset"], 512) raw_key = reader.read(key_match["offset"], 20) # Stage 1 — Base64 decode (malware stored config as base64) try: decoded = b64(raw_config.rstrip(b"\\x00")) except Exception: return {"status": "decode_failed", "config": {}} # Stage 2 — RC4 decrypt with key from the second YARA match plaintext = rc4(decoded, raw_key) # Stage 3 — Parse the plaintext structure (family-specific) c2_host = plaintext[:64].rstrip(b"\\x00").decode("ascii") c2_port = struct.unpack_from("<H", plaintext, 64)[0] sleep = struct.unpack_from("<I", plaintext, 66)[0] return { "status": "success", "config": {"c2": c2_host, "port": c2_port, "sleep_ms": sleep} }
// WHAT THE EXTRACTOR DECIDES — cfgx NEVER TOUCHES THESE

Which YARA matches are relevant · How many bytes to read · Where the config starts relative to the match offset · Whether bytes are encrypted, encoded, or raw · Which algorithm to apply · What key, IV, nonce, or increment is needed · The order of multiple algorithm stages · How to parse the resulting plaintext · What the configuration fields are named · What status string to return

EXTRACTOR RESULT CONTRACT

Every family extractor returns a Python dict with two keys: status and config. cfgx checks this before saving the result.

FIELD TYPE REQUIRED DESCRIPTION
status str yes Any string — cfgx does not restrict the value. Use whatever is meaningful to your workflow: "success", "not_found", "decryption_failed", "partial", "invalid_config". The framework records it as-is.
config any yes Intentionally not limited. Can be a list, a dict, a nested structure, or an empty collection. You define the schema — cfgx serialises it to JSON exactly as returned. The field must be present even when extraction fails (return [] or {}).
STATUS VALUES — EXAMPLES
VALID RETURN EXAMPLES# Full success {"status": "success", "config": {"c2": "evil.com", "port": 443}} # YARA matched but no config found at the offset {"status": "not_found", "config": []} # Decryption ran but produced garbage (wrong key) {"status": "decryption_failed", "config": {}} # Some values extracted but config was incomplete {"status": "partial", "config": [{"c2": "evil.com"}]} # Any custom status is valid — cfgx records it unchanged {"status": "sample_is_unpacked_stub", "config": {}}
FULL MATCH OBJECT REFERENCE
FIELD TYPE ALWAYS PRESENT DESCRIPTION
rule str yes YARA rule name — e.g. "VoidStealer"
identifier str yes YARA string identifier — e.g. "$steamid", "$c2_url", "$config"
offset int yes Raw file offset of this string occurrence. Pass directly to reader.read()
section str | None PE/ELF only PE section name — e.g. ".rdata", ".data", ".text". None for header/overlay regions
rva int | None PE/ELF only Relative Virtual Address. Useful for comparing with IDA Pro or Binary Ninja
va int | None PE/ELF only Full Virtual Address = ImageBase + RVA. Matches the address you see in a live debugger session
ALGORITHM LIBRARY

cfgx ships a reusable algorithm library that family extractors can import directly. These are generic, thoroughly tested cryptographic and encoding primitives — the family extractor decides which algorithm the malware uses, in what order, and with what settings. The framework never auto-tries algorithms against YARA matches.

The library exists to prevent every analyst from reimplementing the same RC4, Base64, and XOR code for each malware family. Import what you need, chain what the malware uses, ignore the rest.

ENCODINGS
Base16 Base32 Base45 Base58 Base64 Base85
TRANSFORMS

CIPHERS

HASHES
MD5 SHA1 SHA256
// ALGORITHMS ARE NOT AUTOMATICALLY TRIED

cfgx never runs Base64 → RC4 → AES on every match hoping something decodes. That approach produces false positives and is impossible to interpret reliably. Instead: the analyst reverse-engineers the malware, identifies the exact algorithm chain, and writes a extractor that matchs it. The algorithm library provides the building blocks — the analyst provides the knowledge of how to assemble them.

ENCODINGS — BINARY TO TEXT
Base16 (Hex) from cfgx.algorithms.base16 import decode

Represents each byte as two hexadecimal characters. Every byte → two hex digits. The output is always exactly twice the length of the input. Common in malware that stores SHA256 hashes, encryption keys, or configuration checksums as hex strings embedded in the binary. Decode converts the hex string back to raw bytes for further processing.

# 0x48 0x65 0x6c → "48656c" from cfgx.algorithms.base16 import decode raw = decode("48656c6c6f") # → b"Hello" # Then pass raw bytes to the next algorithm plaintext = rc4(raw, key)
Base32 from cfgx.algorithms.base32 import decode

Binary-to-text encoding using an uppercase alphabet (A–Z, 2–7). The output contains only alphanumeric characters, which makes it ideal for DNS — DNS labels only allow alphanumeric characters, so Base32 is the encoding of choice for DNS C2 tunnelling. Malware encodes stolen data or commands in subdomain labels using Base32. Decode returns raw bytes.

from cfgx.algorithms.base32 import decode raw = decode("JBSWY3DPEB3W64TMMQ======") # → b"Hello World!" # DNS C2 example: malware queries # JBSWY3DP.evil.com — Base32 subdomain
Base45 from cfgx.algorithms.base45 import decode

A compact encoding using 45 characters — more efficient than Base64 for some data types. Originally designed for QR codes. Increasingly appears in modern malware and Python-based loaders. cfgx checks bad input and raises a descriptive error rather than silently producing corrupt output, which is important when the key bytes differ between samples.

from cfgx.algorithms.base45 import decode raw = decode("%69 VD82EI2B.KESTC") # → b"Hello World!"
Base58 from cfgx.algorithms.base58 import decode

A reduced-alphabet encoding (no 0, O, I, l) popularised by Bitcoin for wallet addresses. Malware increasingly uses Base58 to store identifiers, encoded payloads, or C2 addresses in a format that looks like a cryptocurrency address — evading simple string-based detection rules that focus on standard Base64. The output is case-sensitive and variable-length.

from cfgx.algorithms.base58 import decode raw = decode("JxF12TrwUP45BMd") # → b"Hello World!" # Looks like a BTC address — evades obvious # Base64 or hex detection signatures
Base64 from cfgx.algorithms.base64 import decode

The most common encoding in malware config extraction. Used to store configs as printable text in the binary, to transport encrypted bytes over HTTP, and as the first stage before decryption. Base64 is not encryption — it is trivially reversible — but it hides binary data from naive string searches and signature matchers. cfgx handles standard, URL-safe, and padded variants.

from cfgx.algorithms.base64 import decode as b64 from cfgx.algorithms.rc4 import rc4 raw = b64("SGVsbG8gV29ybGQ=") # → b"Hello World" # Most common malware chain: # encoded_config → Base64 decode → RC4 → plaintext plaintext = rc4(b64(encoded_config), hardcoded_key)
Find Base64 usage: look for the alphabet string ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789+/ in the binary. Custom alphabets indicate a modified Base64 — the order of the 64 characters defines the custom mapping.
Base85 from cfgx.algorithms.base85 import decode

More compact than Base64 — encodes 4 bytes as 5 characters, giving 25% overhead versus Base64's 33%. cfgx supports both standard Base85 and ASCII85 variants. Less common than Base64 in malware, but appears in Python-generated payloads and marshal-based packers (Python's marshal.loads(base64.b85decode(...)) is a known stager technique).

from cfgx.algorithms.base85 import decode raw = decode("NM&qnZ!&!&87eHI") # → b"Hello World!"
TRANSFORMS — BIT-LEVEL OPERATIONS
Repeating-Key XOR from cfgx.algorithms.xor import xor

XOR each byte of the data against the matching byte of the key, cycling the key when it is shorter than the data. XOR is its own inverse — applying the same key twice returns the original data, so the same function both encrypts and decrypts. This is the most common obfuscation primitive in malware: cheap to implement, fully reversible, and sufficient to defeat byte-level signatures. The weakness is known-plaintext: if you know any plaintext bytes at a known position, you immediately recover those key bytes.

from cfgx.algorithms.xor import xor # data: A B C D E F G H # key: K E Y K E Y K E ← key cycles # out: A^K B^E C^Y D^K E^E ... plaintext = xor(ciphertext, b"\\x4b\\x45\\x59") # String keys work too plaintext = xor(ciphertext, "KEY") # Known-plaintext attack: if you know plaintext[0] = 'M' (MZ header) # then key[0] = ciphertext[0] ^ ord('M')
The family extractor must determine the key from the malware's decryption stub — cfgx does not attempt to brute-force or guess it. Look for the key as a hardcoded byte array near the decryption loop, or extract it as a separate YARA match.
Single-Byte XOR from cfgx.algorithms.xor import xor_single_byte

XOR every byte of the data against a single constant key byte. Extremely common for string obfuscation — the entire string or blob is XOR'd with one value (e.g. 0x37, 0x5A, 0xFF). The key is only 1 byte, so if you don't know it, you can try all 256 possibilities in microseconds and look for printable output. In disassembly: look for XOR [reg+offset], imm8 in a tight loop — the immediate value is the key.

from cfgx.algorithms.xor import xor_single_byte # Key is one byte — 0x00 to 0xFF plaintext = xor_single_byte(data, 0x37) ← Mirai's key # If you don't know the key, brute-force all 255: for k in range(1, 256): result = xor_single_byte(data, k) if b"http" in result or b".exe" in result: print(f"Key 0x{k:02x}:", result)
Mirai botnet used single-byte XOR with key 0x37 for all config strings. If null bytes appear in the ciphertext (common in PE files), XOR'ing them with any key reveals that key byte directly.
Rolling XOR from cfgx.algorithms.xor_rolling import rolling_xor

Like repeating-key XOR, but the key itself changes after each byte — typically by adding a fixed increment value. This makes frequency analysis harder than single-byte XOR because the effective key changes every step. The analyst must identify both the initial key byte and the increment from the malware's decryption stub. In disassembly: look for an ADD or INC instruction on the key register inside the decryption loop, alongside the XOR.

from cfgx.algorithms.xor_rolling import rolling_xor # initial_key=0x37, increment=1: # step 0: data[0] ^ 0x37 # step 1: data[1] ^ 0x38 (0x37 + 1) # step 2: data[2] ^ 0x39 (0x38 + 1) # ... # increment=3: # step 0: data[0] ^ 0x37 # step 1: data[1] ^ 0x3a (0x37 + 3) # step 2: data[2] ^ 0x3d (0x3a + 3) plaintext = rolling_xor(data, initial_key=0x37, increment=1)
Common in custom-packed PE loaders. The disassembly pattern: XOR [esi], al followed by ADD al, N or INC al inside a loop — where al is the rolling key register.
CIPHERS — ENCRYPTION
RC4 from cfgx.algorithms.rc4 import rc4

The most abused stream cipher in malware. RC4 is identified by a 256-byte state array (S-box) initialised to values 0–255, followed by a key-mixing loop (KSA) and then a keystream-generation loop (PRGA). Cryptographically broken since the early 2000s, but malware authors don't care — it only needs to defeat static signatures, not nation-state cryptanalysis. RC4 is symmetric: the same function decrypts and encrypts. The key can be any length from 1 to 256 bytes.

from cfgx.algorithms.rc4 import rc4 # Key can be bytes or string — any length 1–256 bytes plaintext = rc4(ciphertext, "74934157919546113795") # Most common chain seen in malware (StealC, Emotet, TrickBot): decoded = b64(raw_config) plaintext = rc4(decoded, hardcoded_rc4_key)
Identify in binary: KSA = 256-iteration loop initialising S[0..255] = 0..255, then a second 256-iteration swap loop. The key is usually a hardcoded byte array or ASCII string passed to the KSA function. Disassembly: two nested loops over 256 iterations with swap operations are unmistakable.
AES from cfgx.algorithms.aes import decrypt_cbc, decrypt_ecb, decrypt_ctr

The dominant block cipher in modern malware. Ransomware uses AES-256-CBC for file encryption, C2 frameworks use AES-128-CBC or AES-256-GCM for traffic, loaders use AES-ECB for payload decryption. cfgx supports ECB, CBC, and CTR modes with 128, 192, or 256-bit keys. The analyst must identify the mode, key, and IV from the malware — cfgx does not guess. CBC requires a 16-byte IV, usually prepended to the ciphertext or hardcoded nearby. ECB has no IV (dangerous — identical plaintext blocks produce identical ciphertext). CTR is stream-like, no padding.

from cfgx.algorithms.aes import decrypt_cbc, decrypt_ecb, decrypt_ctr # CBC — most common in ransomware and C2 frameworks # IV is often prepended to ciphertext (first 16 bytes) iv = ciphertext[:16] payload = ciphertext[16:] plaintext = decrypt_cbc(payload, key=aes_key, iv=iv) # ECB — no IV, each 16-byte block is independent plaintext = decrypt_ecb(ciphertext, key=b"sixteenbyteskey!") # CTR — stream mode, variable-length output, no padding needed plaintext = decrypt_ctr(ciphertext, key=aes_key, nonce=nonce)
Identify AES: S-box starts with 63 7C 77 7B, Rcon table starts with 01 02 04 08 10 20 40 80 1B 36. AES-NI: look for AESENC / AESENCLAST instructions (opcode 66 0F 38 DC / DD). WinAPI: BCryptEncrypt with BCRYPT_AES_ALGORITHM or CALG_AES_256.
DES from cfgx.algorithms.des import decrypt_cbc, decrypt_ecb

A legacy 64-bit block cipher with a 56-bit effective key — cryptographically broken since 1998 (brute-forceable in under 24 hours). Still found in older malware and banking trojans that target legacy Windows CryptoAPI. Key is 8 bytes (64 bits, but only 56 are effective — one bit per byte is a parity bit). Block size is 8 bytes. 16 Feistel rounds. CBC mode requires an 8-byte IV.

from cfgx.algorithms.des import decrypt_cbc, decrypt_ecb # 8-byte key, ECB mode plaintext = decrypt_ecb(ciphertext, key=b"secret01") # 8-byte key, 8-byte IV, CBC mode plaintext = decrypt_cbc(ciphertext, key=b"secret01", iv=b"\\x00"*8)
Identify: 8 S-boxes (each 64 bytes), initial permutation table starting 58 50 42 34 26 18 10 02. WinAPI: CALG_DES in CryptEncrypt calls. Primarily seen in Zeus, SpyEye, and other banking trojans from the 2010s era.
3DES (Triple DES) from cfgx.algorithms.des3 import decrypt_cbc, decrypt_ecb

Applies DES three times with up to three independent keys. More secure than single DES (effective key length of 112 or 168 bits) but deprecated for new use since 2023. Still present in legacy malware and any sample that uses Windows CryptoAPI with CALG_3DES. 16-byte key (2-key: K1-K2-K1 pattern) or 24-byte key (3-key: K1-K2-K3). CBC requires an 8-byte IV.

from cfgx.algorithms.des3 import decrypt_cbc # 16-byte key (2-key 3DES) or 24-byte key (3-key 3DES) plaintext = decrypt_cbc( ciphertext, key=b"16-or-24-byte-key!!!"[:16], iv=b"\\x00"*8 )
Zeus botnet used 3DES for config encryption alongside RC4. If you see CALG_3DES in WinAPI traces or a 24-byte hardcoded key in the binary, this is the algorithm. The tripled DES structure (three separate key schedules) is visible in the key expansion code.
Blowfish from cfgx.algorithms.blowfish import decrypt_cbc, decrypt_ecb

A fast Feistel cipher with variable key length (32–448 bits). Its most distinctive feature is a massive key schedule that produces four 256-entry S-boxes and an 18-entry P-array — all derived from the hexadecimal digits of π. The constant P[0] = 0x243F6A88 (first digits of π in hex) is its universal identifier and makes YARA detection trivial. Found in older RATs, backdoors, and some ransomware from the 2015–2018 era.

from cfgx.algorithms.blowfish import decrypt_cbc # Variable-length key: 4 to 56 bytes # Block size: 8 bytes, CBC uses 8-byte IV plaintext = decrypt_cbc( ciphertext, key=b"variable_len_key", iv=b"\\x00"*8 )
YARA identification: P[0] = 0x243F6A88, P[1] = 0x85A308D3. S-box[0] starts with D1310BA6 98DFB5AC. The 16KB S-box structure is unmistakable in a hex dump — look for a large data block starting with these π-derived constants.
ChaCha20 from cfgx.algorithms.chacha20 import decrypt

A modern, fast stream cipher used in TLS 1.3, WireGuard, and increasingly in advanced malware. Identified by the ASCII constant "expand 32-byte k" (hex: 61707865 3320646E 79622D32 6B206574) that initialises the 512-bit state matrix. 256-bit key, 96-bit nonce (IETF variant). Because ChaCha20 is a stream cipher, there is no padding and the output is always the same length as the input. Used by BlackCat/ALPHV and Brute Ratel C4.

from cfgx.algorithms.chacha20 import decrypt # 32-byte key, 12-byte nonce, optional counter (usually 0) plaintext = decrypt( ciphertext, key=b"\\x00"*32, nonce=b"\\x00"*12, counter=0 ) # Identify: search for "expand 32-byte k" as a string # or its hex: 61707865 3320646E 79622D32 6B206574
The quarter-round operations (ADD + XOR + rotate) with rotation constants 16, 12, 8, 7 are distinctive in disassembly. YARA: { 61 70 78 65 33 20 64 6e 79 62 2d 32 6b 20 65 74 } is a strong signature for both ChaCha20 and Salsa20.
ChaCha20-Poly1305 from cfgx.algorithms.chacha20_poly1305 import decrypt

ChaCha20 combined with the Poly1305 MAC — provides authenticated encryption (AEAD). The authentication tag (16 bytes) must be present and valid for decryption to succeed — a wrong key or corrupted ciphertext fails authentication and raises an error rather than returning garbage. Used in modern C2 frameworks (Brute Ratel C4 uses ChaCha20-Poly1305 for all C2 traffic). The tag is usually appended to the ciphertext.

from cfgx.algorithms.chacha20_poly1305 import decrypt # tag is the 16-byte authentication tag # Usually appended as the last 16 bytes of the ciphertext plaintext = decrypt( ciphertext=ciphertext[:-16], key=key, ← 32 bytes nonce=nonce, ← 12 bytes tag=ciphertext[-16:], aad=b"" ← additional authenticated data (may be empty) ) # Raises exception if tag invalid — wrong key or corrupt data
HASH FUNCTIONS — ONE-WAY DIGESTS

Hash functions are one-way — they produce a fixed-size digest and cannot be reversed. In config extraction, a extractor uses hashing to match a value the malware derives from a hash, not to decrypt data. Common patterns: deriving an AES key by hashing a hardcoded seed (MD5(seed) → 16-byte key), verifying a downloaded payload matches an expected hash, computing a bot ID from a machine fingerprint, or reproducing API hashing for dynamic import resolution.

MD5 from cfgx.algorithms.md5 import hexdigest, digest

128-bit (16 bytes, 32 hex chars) digest. Broken for collision resistance since 2004 — collisions can be computed in seconds — but still universally used in malware for non-security purposes. Most common uses: deriving an AES-128 key from a hardcoded seed (MD5(seed) → 16 bytes), generating a bot ID from a machine fingerprint (MD5 of MAC address + hostname + volume serial), and verifying dropped files. Identified by init constants: 0x67452301 0xEFCDAB89 0x98BADCFE 0x10325476 in little-endian.

from cfgx.algorithms.md5 import hexdigest, digest # hexdigest returns the 32-char hex string value = hexdigest(b"data") # → "8d777f385d3dfec8815d20f7496026dc" # digest returns raw 16 bytes — use directly as AES-128 key aes_key = digest(b"hardcoded_seed") plaintext = decrypt_cbc(ciphertext, aes_key, iv=b"\\x00"*16)
Identify in binary: constants 01 23 45 67 (H0 in LE), 89 AB CD EF (H1), FE DC BA 98 (H2), 76 54 32 10 (H3). Round constants table: 64 entries starting with D76AA478.
SHA1 from cfgx.algorithms.sha1 import hexdigest, digest

160-bit (20 bytes, 40 hex chars) digest. Broken for collision resistance (SHAttered attack, 2017) but still widely used in malware for key derivation and HMAC construction. PBKDF2-SHA1 is common for deriving encryption keys from passwords. HMAC-SHA1 appears in C2 authentication schemes. Shares init constants H[0]–H[3] with MD5 — distinguish by the additional H[4] = 0xC3D2E1F0 which is unique to SHA-1.

from cfgx.algorithms.sha1 import hexdigest, digest value = hexdigest(b"data") # → "a94a8fe5ccb19ba61c4c0873d391e987982fbbd3" # Raw bytes for key derivation or HMAC construction key_material = digest(b"seed") # → 20 raw bytes
Identify: H[4] init = 0xC3D2E1F0 (LE: F0 E1 D2 C3) uniquely distinguishes SHA-1 from MD5. Round constant K[0] = 0x5A827999. WinAPI: CALG_SHA1 or BCRYPT_SHA1_ALGORITHM.
SHA256 from cfgx.algorithms.sha256 import hexdigest, digest

256-bit (32 bytes, 64 hex chars) digest — the current industry standard. Widely used in modern malware for key derivation (SHA256(hardcoded_seed) → 32-byte AES-256 key), HMAC-SHA256 for C2 message authentication (Cobalt Strike uses HMAC-SHA256 for beacon metadata), and verifying integrity of downloaded second-stage payloads. No practical attacks exist against SHA-256. Identified by H[0] = 0x6A09E667 and first round constant K[0] = 0x428A2F98.

from cfgx.algorithms.sha256 import hexdigest, digest value = hexdigest(b"data") # → "3a6eb0790f39ac87c94f3856b2dd2c5d110e6811602261a9a923d3bb23adc8b7" # 32-byte AES-256 key from hardcoded seed (common modern pattern) aes_key = digest(b"malware_hardcoded_seed_value") plaintext = decrypt_cbc(ciphertext, aes_key, iv=extracted_iv)
Identify: H[0] init = 0x6A09E667 (LE: 67 E6 09 6A), K[0] = 0x428A2F98. Full K table: 64 constants starting 428A2F98 71374491 B5C0FBCF E9B5DBA5. WinAPI: BCRYPT_SHA256_ALGORITHM or CALG_SHA_256.
CHAINING ALGORITHMS

The most important use of the algorithm library is chaining multiple algorithms to match the exact processing sequence found during reverse engineering. The order must exactly match the malware's implementation. If the malware does Base64 → XOR → RC4, the extractor must do the same — reversing the order or substituting one algorithm produces garbage.

MULTI-STAGE CHAIN EXAMPLE — BASE64 → XOR → RC4from cfgx.algorithms.base64 import decode as b64 from cfgx.algorithms.xor import xor from cfgx.algorithms.rc4 import rc4 # Stage 0 — YARA found $config_blob at offset 0x6E368 raw = reader.read(match["offset"], 512) # Stage 1 — malware Base64-decodes the stored blob stage1 = b64(raw.rstrip(b"\\x00")) # Stage 2 — then XORs with a 4-byte repeating key stage2 = xor(stage1, b"\\x4b\\x3a\\x11\\x7f") # Stage 3 — then RC4 with a hardcoded numeric key stage3 = rc4(stage2, "74934157919546113795") # Stage 4 — analyst interprets the plaintext c2_host = stage3[:64].rstrip(b"\\x00").decode("ascii") c2_port = int.from_bytes(stage3[64:66], "little") sleep = int.from_bytes(stage3[66:70], "little")
ERROR HANDLING

cfgx checks every step of the pipeline and produces exact, descriptive error messages. All errors are caught at the framework level — a extractor exception does not crash cfgx, it reports the error and continues to the next sample in batch mode.

CAUSE ERROR MESSAGE EXPLANATION
Extractor has no extract() [ERROR] Analyst extractor must define extract(matches, reader) The extractor file was loaded but no extract attribute exists at module level — check the function name spelling
extract is not callable [ERROR] Analyst extractor 'extract' must be callable A variable named extract exists but is not a function — e.g. extract = "not a function"
Extractor raises exception [ERROR] <exception message> The analyst's code raised an unhandled exception. The message from the exception is forwarded directly so you see what went wrong in your code
Result missing 'config' [ERROR] Result must contain 'config' Returned {"status": "success"} without a config key — both fields are always needed, even on failure
Result missing 'status' [ERROR] Result must contain 'status' Returned {"config": []} without a status key
status is not a string [ERROR] Result 'status' must be a string Returned {"status": 123, "config": []} — status must always be a string, even if it's "0" or "false"
reader.read negative offset ValueError: Offset cannot be negative Passed a negative value to reader.read(offset, size) — file positions start at 0
reader.read negative size ValueError: Size cannot be negative Passed a negative size — zero-byte reads return b"" without error

FILE-BY-FILE GUIDE
FILE ROLE KEY DETAILS
cfgx/cli.py Entry point Parses CLI arguments, checks all three paths, dispatches to single-file or directory processing, writes JSON output, prints terminal results. The user-facing layer — no extraction logic here.
cfgx/main.py Orchestrator process_sample() runs the 10-step pipeline. Connects all framework components. Contains no malware-family logic — it only wires modules together and calls the extractor.
cfgx/extractor.py Extractor manager Two responsibilities: (1) dynamically load a Python file as a module, (2) validate the returned result dict has the correct structure and types. The boundary between cfgx and analyst code.
cfgx/reader.py Byte access SampleReader class with read(offset, size). Validates all inputs, handles EOF gracefully. The extractor never touches the file directly.
cfgx/models.py Type definitions Match (rule+identifier+offset), PEMetadata (section+rva+va), PEMatch (combined), ExtractionResult (status+config). TypedDicts for static analysis support.
formats/pe.py PE parser load_pe, get_section_for_offset, offset_to_rva, rva_to_va, resolve_offset. All PE metadata resolution happens here, keeping it out of the orchestration layer.
formats/elf.py ELF parser Mirrors pe.py for ELF binaries. Section identification, VA resolution, file-offset-to-VA conversion. Used for Linux and IoT malware samples.
formats/detect.py Format detector Identifies the binary format from magic bytes (MZ for PE, 0x7F ELF for ELF). Determines which parser to use before loading.
yara_handler/runner.py YARA runner Compiles the rule, scans the sample, flattens all match instances into a list of normalized Match dicts. One dict per occurrence — each with rule, identifier, and file offset.
cfgx/algorithms/ Algorithm library 16 independent Python modules, each providing encode/decode or encrypt/decrypt functions. No dependencies between algorithm modules — import only what you need.
extractor.py Example extractor Working VoidStealer family extractor — demonstrates match filtering, reader.read(), value interpretation, and result construction. A practical starting template.
bad_extractor.py Negative test Intentionally broken extractor used to test cfgx error handling. Tests: missing extract(), non-callable extract, extractor exceptions, missing config, invalid status type.
pyproject.toml Package config Defines name, version, Python requirement, dependencies, and the [project.scripts] entry that registers the cfgx command after pip install -e ..
