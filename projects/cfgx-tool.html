cfgx — Config Extraction Framework

OVERVIEW

Extracting malware configurations is tedious — every family requires the same boilerplate: load the sample, run YARA, find the interesting bytes, resolve PE offsets, read the config, parse it, report it. cfgx handles all of that. You only write the part that's specific to the malware family you're analysing.

The framework's core design principle: cfgx provides evidence and controlled access to the sample. The analyst plugin decides what that evidence means. The framework never knows whether $Config means a configuration or something else — that interpretation lives entirely in your plugin/extractor.

This means you can reuse the same cfgx installation for RedLine, Lumma, VoidStealer, StealC, or any future family — just swap the YARA rule and the analyst plugin.

EXTRACTION PIPELINE
Every sample goes through the same 10-step pipeline. Steps 1–7 are handled by cfgx. Step 8 is yours.
01 CLI Validate Verify YARA rule path, sample path, and plugin path all exist and are the correct types
↓
02 Load Plugin Dynamically import the analyst plugin, verify it exposes a callable extract(matches, reader)
↓
03 Load PE / ELF Parse the sample as a PE or ELF binary — identifies sections, image base, entry point
↓
04 YARA Scan Compile the rule, scan the sample, emit one Match object per string occurrence (not per rule)
↓
05 Normalize Matches Convert raw YARA results into generic { rule, identifier, offset } structures
↓
06 Resolve PE Metadata Enrich each match: file offset → PE section → RVA → VA. Adds section, rva, va fields
↓
07 Create SampleReader Wrap the sample file handle in a validated reader — reader.read(offset, size) is the only access path
↓
08 plugin.extract() Your code runs here. Select matches, read bytes, decrypt/decode, return structured config
↓
09 Validate Result Verify the plugin returned { status: str, config: any } — rejects malformed results with clear errors
↓
10 Output Print to terminal + write rule-name.json to output directory (combined for batch runs)

WRITING AN ANALYST PLUGIN

A plugin is a plain Python file that exports a single function: extract(matches, reader). That's the entire interface. cfgx calls it with the enriched YARA matches and the SampleReader. You decide what to do with them.

PLUGIN EXAMPLEdef extract(matches, reader): results = [] for match in matches: # Only interested in one specific YARA string if match["identifier"] != "$steamid": continue # Read 16 bytes from that file offset data = reader.read(match["offset"], 16) # Interpret as ASCII — only the plugin knows what this means results.append({ "identifier": match["identifier"], "offset": match["offset"], "section": match.get("section"), # .rdata, .data, etc. "rva": match.get("rva"), # resolved by cfgx "value": data.decode("ascii"), }) # Return the contract: status (str) + config (anything) return { "status": "success", "config": results, }

The matches list is flat — if $steamid appears 3 times, you get 3 match objects. Each one includes: rule, identifier, offset, and (when PE info is available) section, rva, va.

The reader.read(offset, size) call validates bounds and returns raw bytes. From there, decryption, base64 decoding, struct unpacking — all yours.

PLUGIN RESULT CONTRACT
Every plugin must return a dict with exactly these two keys. cfgx validates this before writing output.
FIELD TYPE DESCRIPTION
status str Any string — cfgx doesn't restrict the value. Use "success", "not_found", "decryption_failed", "partial", or anything meaningful to your analysis workflow.
config any Intentionally unrestricted. Can be a list, dict, string, or nested structure. You define the schema — cfgx serialises it to JSON as-is.
MATCH OBJECT SCHEMA
FIELD TYPE DESCRIPTION
rule str Name of the matching YARA rule (e.g. "VoidStealer")
identifier str YARA string identifier (e.g. "$steamid", "$c2_url")
offset int Raw file offset of this string occurrence — pass directly to reader.read()
section str? PE section name (e.g. ".rdata", ".data") — None for non-PE targets
rva int? Relative Virtual Address — offset from image base. Useful for cross-referencing IDA or x64dbg
va int? Full Virtual Address (ImageBase + RVA) — matches addresses in a live debugger session

DESIGN PHILOSOPHY

The central design principle of cfgx is simple: the framework provides evidence and controlled access to the sample; the analyst plugin decides what that evidence means.

The core is deliberately malware-family agnostic. cfgx can know that a YARA rule named VoidStealer matched $steamid at offset 450664, but it does not decide that the value is a Steam ID. That interpretation belongs to the analyst plugin.

This separation lets one cfgx installation support different families by changing the YARA rule and plugin instead of modifying the framework itself.

FOLDER / BATCH ANALYSIS

When the sample argument is a directory, cfgx processes each file independently through the extraction pipeline and then combines the results into one JSON report named after the YARA rule.

COMMANDcfgx D:\rules\voidstealer.yar D:\samples\test_samples D:\plugins\voidstealer.py --output results # Example input directory test_samples/ ├── sample └── sample2 # Final output results/ └── voidstealer.json

For example, sample → YARA → PE → plugin → result and sample2 → YARA → PE → plugin → result are combined into the same rule-level report. This allows multiple samples belonging to the same malware family/rule to be represented together.

HOW CFGX WORKS

1. CLI validation. cfgx verifies that the YARA rule exists and is a file, the sample path exists and is a file or directory, and the analyst plugin exists and is a file.

2. Analyst plugin loading. The external Python plugin is loaded dynamically and is never hard-coded into the framework.

3. PE loading. PE samples are loaded with pefile so YARA offsets can be enriched with section and address information.

4. ELF support. The project includes ELF loading, section identification, virtual address resolution, and file-offset-to-virtual-address resolution.

5. YARA scanning. The rule is compiled and executed. Every individual string instance becomes its own generic match.

6. PE metadata enrichment. A file offset can be resolved into a PE section, RVA, and virtual address.

7. SampleReader. The plugin receives controlled access through reader.read(offset, size) rather than the sample path or raw file handle.

8. Analyst extraction. cfgx calls extract(matches, reader). The plugin selects matches, reads bytes, decrypts/decodes data when needed, and builds its configuration.

9. Result validation. cfgx requires a dictionary containing status and config, with status being a string.

10. Output. The result is displayed in the terminal and saved as JSON.

YARA PROCESSING

YARA processing lives in yara_handler/runner.py. The runner compiles the rule, scans the sample, iterates through matches and their string instances, and converts them into a flat list of normalized match objects.

MATCH{ "rule": "VoidStealer", "identifier": "$steamid", "offset": 450664 } # Repeated occurrences remain separate $steamid → offset 450664 $steamid → offset 450688 $steamid → offset 450712

The framework intentionally treats YARA matches as evidence/anchors, not automatically as configuration data. If one YARA string occurs three times, cfgx produces three independent matches.

PE & ELF PROCESSING

PE functionality is implemented in formats/pe.py. The module loads PE files, locates sections, converts file offsets to RVAs, converts RVAs to virtual addresses, and enriches YARA matches with that metadata.

PE RESOLUTIONfile offset ↓ PE section ↓ RVA ↓ VA = ImageBase + RVA # Example resolved metadata{ "section": ".rdata", "rva": 456992, "va": 5369166112 }

The repository also documents ELF support for loading, section identification, virtual-address resolution, and file-offset-to-virtual-address resolution.

SAMPLEREADER

cfgx/reader.py provides the SampleReader abstraction. Its primary API is:

data = reader.read(450664, 16) # raw bytes can then be interpreted by the analyst plugin value = data.decode("ascii")

The reader validates offsets and sizes before accessing the sample. The plugin does not receive the sample path or file handle, keeping sample access behind the framework's controlled reader interface.

The repository testing covers normal reads, different read sizes, multiple independent reads, negative offsets, negative sizes, and reads beyond EOF.
