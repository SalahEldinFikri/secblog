SeroRAT: Analysis of an AES-256-CBC Dropper with PPID Spoofing

📅 2026 ⏱ 10 MIN READ ✍ SalahEldin Kamil HIGH
Analysis of a dropper (MD5: cfaa9eead8f27ecc01803a5eb9fc463c) that resolves BCrypt APIs via XOR obfuscation, decrypts a 9MB AES-256-CBC payload, drops it as msedge_08X.exe under a Microsoft Edge-mimicking path, then spawns it with explorer.exe as the spoofed parent process.

1. Execution Flow Overview

The dropper executes in four distinct phases before handing off to the SeroRAT payload:

①GetTickCount
timing delay
②XOR resolve
BCrypt APIs
③AES-256-CBC
decrypt payload
④Drop to disk
msedge_08X.exe
⑤Find explorer.exe
PID enumeration
⑥PPID spoof
spawn as child
①
Timing delay — Immediately calls GetTickCount and computes Sleep((GetTickCount() & 0x7F) + 1400), introducing a ~1.4–1.5 second delay before any payload processing. A lightweight sandbox-evasion technique — automated sandboxes with short execution windows miss the detonation entirely.
②
XOR-obfuscated API resolution — Embedded API name strings are XOR-encoded with 0xAA. The dropper decodes them at runtime, then resolves bcrypt.dll and all required BCrypt function pointers via LoadLibrary + GetProcAddress. No BCrypt imports appear in the static IAT.
③
AES-256-CBC payload decryption — Initialises the BCrypt AES provider in CBC mode, imports the hardcoded 256-bit key and 16-byte IV, and decrypts the 9,020,432-byte embedded payload into a heap buffer. Two-pass BCryptDecrypt: first call calculates output size, second performs actual decryption with block padding.
④
Payload drop — Constructs the drop path: %LOCALAPPDATA%\Temp\MicroSoft\Windows\msedge_08X.exe. The filename mimics a legitimate Microsoft Edge executable to blend with normal process listings. Creates the file and writes the decrypted payload.
⑤
Process enumeration — Iterates the running process list via CreateToolhelp32Snapshot + Process32First / Process32Next to locate explorer.exe and extract its PID.
⑥
PPID spoofing & launch — Calls InitializeProcThreadAttributeList then UpdateProcThreadAttribute(PROC_THREAD_ATTRIBUTE_PARENT_PROCESS) with the explorer.exe handle. Spawns msedge_08X.exe via CreateProcess — the resulting process appears in Task Manager and Sysmon as a child of explorer.exe, not the dropper.
Figure 1 — Main function: GetTickCount delay → BCrypt API resolution → AES decrypt → drop → PPID-spoofed spawn

2. XOR Obfuscation & BCrypt API Resolution

All BCrypt-related strings are stored XOR-encoded in the binary with the key 0xAA. At runtime the dropper decodes them and resolves the following functions from bcrypt.dll:

BCryptOpenAlgorithmProvider
Opens the AES algorithm provider
BCryptSetProperty
Sets CBC chaining mode on the provider
BCryptGetProperty
Queries key object size before allocation
BCryptGenerateSymmetricKey
Imports the 256-bit AES key
BCryptDecrypt
Two-pass: size query then actual decryption
BCryptDestroyKey
Cleans up the key handle post-decrypt
BCryptCloseAlgorithmProvider
Releases the algorithm provider handle
Detection note: No BCrypt imports in the IAT. Static analysis will not reveal the crypto capability. Hook GetProcAddress at entry or place a breakpoint on the XOR decode loop (look for the xor byte ptr [reg], 0AAh pattern) to recover all decoded strings before the API resolver runs.
Figure 2 — XOR decode loop (key 0xAA) decoding BCrypt API names, followed by LoadLibrary + GetProcAddress resolution

3. AES-256-CBC Payload Decryption

After the BCrypt handles are initialised, the dropper decrypts its embedded 9,020,432-byte payload using AES-256-CBC with the following hardcoded key material:

AES-256-CBC

The decryption procedure:

  • Provider init — BCryptOpenAlgorithmProvider opens the AES provider; BCryptSetProperty sets the chaining mode to BCRYPT_CHAIN_MODE_CBC.
  • Key import — BCryptGetProperty queries the required key object size; a heap buffer is allocated; BCryptGenerateSymmetricKey imports the 32-byte AES key into the provider.
  • Two-pass decrypt — First BCryptDecrypt call with NULL output buffer calculates the required plaintext size. Second call decrypts into the allocated Decrypted_Data buffer using BCRYPT block padding and the 16-byte IV.
  • Cleanup — Key handle, algorithm provider, allocated buffers, and the bcrypt.dll handle are all released before the function returns the decrypted payload pointer.
Figure 3 — AES-256-CBC decryption: BCryptGenerateSymmetricKey with hardcoded key/IV and two-pass BCryptDecrypt

4. Payload Drop & Path Construction

The dropper constructs the payload path programmatically rather than hardcoding it, making it slightly more resilient to simple string searches:

%LOCALAPPDATA%
\Temp
\MicroSoft\Windows
msedge_08X.exe

Full resolved path: %LOCALAPPDATA%\Temp\MicroSoft\Windows\msedge_08X.exe

Masquerading: The filename msedge_08X.exe is chosen to resemble a legitimate Microsoft Edge browser component. The intermediate directory MicroSoft\Windows (note the capital S) further mimics Microsoft system paths. Defenders should alert on PE file creation in %LOCALAPPDATA%\Temp\ with names containing msedge outside the official Edge install path.
Figure 4 — Path construction: LOCALAPPDATA → \Temp\MicroSoft\Windows\msedge_08X.exe, CreateFile + WriteFile

5. PPID Spoofing via explorer.exe

After writing the payload to disk, the dropper performs parent process ID (PPID) spoofing to disguise the spawned SeroRAT process as a legitimate child of explorer.exe.

①
Process enumeration — CreateToolhelp32Snapshot(TH32CS_SNAPPROCESS) + Process32First / Process32Next iterates all running processes until explorer.exe is found. Records its PID.
②
Handle acquisition — OpenProcess(PROCESS_ALL_ACCESS, explorer_PID) obtains a handle to the explorer.exe process with full access rights.
③
Attribute list setup — InitializeProcThreadAttributeList allocates an extended attribute list for process creation. UpdateProcThreadAttribute(PROC_THREAD_ATTRIBUTE_PARENT_PROCESS) sets the explorer.exe handle as the designated parent.
④
Spoofed launch — CreateProcess with EXTENDED_STARTUPINFO_PRESENT and the prepared attribute list spawns msedge_08X.exe. The OS registers explorer.exe's PID as the parent — Sysmon EID 1 and Task Manager will show the SeroRAT process as a child of explorer.exe, not the dropper.
Detection: Despite PPID spoofing, Sysmon EID 1 records both the nominal parent (explorer.exe) and the actual creating process. The ParentProcessId field will show explorer.exe's PID, but the ParentImage hash will not match any expected explorer.exe child. Alert on msedge_08X.exe or any Edge-named binary spawning from %LOCALAPPDATA%\Temp\. Additionally, GetProcessAffinityMask is called — possibly to verify the explorer.exe handle is valid before proceeding.
Figure 5 — PPID spoofing: Process32First/Next finds explorer.exe PID → InitializeProcThreadAttributeList → UpdateProcThreadAttribute → CreateProcess with spoofed parent
