REVERSE ENGINEERING INFOSTEALER WINDOWS MaaS YARA

Stealc Stealer: Technical Reverse Engineering Report

📅 2025 ⏱ 12 MIN READ ✍ SalahEldin Kamil HIGH
Full reverse engineering of a Stealc stealer sample. The binary resolves all operational strings at runtime using Base64 + RC4 decryption, then performs dynamic API resolution before conducting host fingerprinting, CIS-region evasion, browser credential extraction (Chromium + Firefox), Steam/Outlook/WinSCP data theft, desktop screenshot capture, and PowerShell-based loader execution — all exfiltrated to a typosquatted Cloudflare-mimicking C2 domain.

1. Execution Flow Overview

The sample follows a clean, sequential execution pattern across five distinct phases before exfiltration begins:

①
String decryption — All operational strings (API names, C2 address, configuration keys, file paths) are encrypted at rest using Base64 + RC4 with the key ZFNBF0SzMim7hC3npM. Decryption runs first, populating an in-memory string table used throughout.
②
Dynamic API resolution — Using the decrypted DLL and API name strings, the malware calls LoadLibraryA then GetProcAddress for each required function and stores the resolved pointer in a global variable for later use. No static imports are visible for these APIs.
③
Host fingerprinting — Collects username, NetBIOS name, locale/language, keyboard layouts, OS version, CPU, RAM, GPU, display resolution, timezone, running process list, and installed software. Constructs a system_info.txt report.
④
CIS region check — Queries GetUserDefaultLangID and terminates via ExitProcess if a Russian/CIS language is detected. See Section 4.
⑤
Data collection & exfiltration — Browsers, Steam, Outlook, WinSCP, screenshot, and file collection tasks are dispatched. Each output is uploaded to the C2 as an encrypted blob via HTTP POST.

2. String Obfuscation — Base64 + RC4

Every operational string is stored encrypted in the binary and decrypted at runtime before first use. The decryption routine applies two transformations in sequence:

plaintext = RC4( key="ZFNBF0SzMim7hC3npM", data=Base64Decode( ciphertext ) )

A secondary RC4 key I9r3h5kFEzqWqq0I was observed in the sample, likely used for configuration or data encryption distinct from the string table key.

3. Dynamic API Resolution

After string decryption, the malware builds its API table entirely at runtime. For each required function it calls LoadLibraryA with the decrypted DLL name, then GetProcAddress with the decrypted function name, and stores the resolved pointer in a global variable. Static import analysis reveals only the bootstrap functions — all 90+ operational APIs are invisible to standard IAT inspection.

Analysis note: To enumerate all resolved APIs, hook GetProcAddress at the debugger entry point and log all calls before the malware's main logic begins. Alternatively, dump the global pointer table after the API resolver returns — all function pointers are populated contiguously.
Figure 2 — Dynamic API resolver: LoadLibraryA + GetProcAddress loop storing pointers in global variable table

4. Host Fingerprinting & CIS Region Evasion

Following API resolution, the malware collects a detailed victim profile before performing any data theft. This profile is assembled into system_info.txt and uploaded to C2 as the first exfiltrated object.

Fields collected:

  • Network: external IP, country (ISO code)
  • Identity: HWID (volume serial), username, computer name, OS version + build, architecture
  • Hardware: CPU model + core/thread count, RAM total, GPU model, display resolution + color depth per monitor
  • Locale: local time, UTC time, timezone, keyboard layouts, system language
  • Software: full installed application list from SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall
  • Processes: running process list via CreateToolhelp32Snapshot + Process32FirstW/NextW
  • Power: battery/power status via GetSystemPowerStatus (laptop detection)

Immediately after fingerprinting, the malware queries GetUserDefaultLangID and compares the result against the following language IDs:

Russian — 1049 Ukrainian — 9 Belarusian — 1 Kazakh — 28 Uzbek — 4

If any of these languages is detected, the malware immediately calls ExitProcess — a standard CIS operator protection clause common to most Russian-developed MaaS stealers.

5. Data Collection Modules

5.1 Browser Credential & Cookie Theft

The browser module iterates a task list dispatching each entry to the appropriate collection routine based on task type: browser data (SQLite), browser-specific info, or cookie extraction. Chromium-based browsers are handled via DPAPI (CryptUnprotectData) for v10 keys and direct os_crypt / encrypted_key extraction for v20. Firefox credentials are decrypted via PK11SDR_Decrypt from the dynamically loaded nss3.dll.

Locked database files are handled by the Restart Manager (rstrtmgr.dll) — the malware registers the locked file as a resource, uses RmGetList to identify the locking process, terminates it, then accesses the file.

5.2 Steam Session Theft

The Steam module reads the installation path from HKCU\Software\Valve\Steam → SteamPath, constructs the config directory path, then collects the following files:

  • ssfn* — Steam Guard session tokens
  • config.vdf — Account configuration
  • loginusers.vdf — Remembered login accounts
  • DialogConfig.vdf / DialogConfigOverlay*.vdf — UI configuration
  • libraryfolders.vdf — Library path configuration
Figure 6 — Steam module: registry path resolution and targeted Steam config file collection

5.3 Outlook Data Collection

Iterates Outlook-related registry entries, extracts account strings and profile information, combines them into a buffer, and uploads via UploadEncryptedData. Output stored remotely as soft\Outlook\outlook.txt. Controlled by the steal_outlook configuration flag.

Figure 7 — Outlook module: registry entry iteration and encrypted upload to soft\Outlook\outlook.txt

5.4 WinSCP Session Harvesting

Enumerates all WinSCP stored sessions from Software\Martin Prikryl\WinSCP 2\Sessions. For each session it extracts: session name, host, port, username, and password. If a session is password-protected with a master password or is empty, that status is recorded instead. Output formatted as a text report and uploaded as soft\WinSCP\winscp.txt.

Figure 8 — WinSCP module: session enumeration from registry, credential extraction with master-password handling

5.5 Desktop Screenshot

When the take_screenshot config flag is set, the malware captures the full desktop using a standard GDI → GDI+ pipeline: GetDC → CreateCompatibleDC → CreateCompatibleBitmap → BitBlt to capture pixels, then GdipCreateBitmapFromHBITMAP → GdipSaveImageToStream → CreateStreamOnHGlobal to encode as JPEG into an in-memory stream. Output: screenshot.jpg.

Figure 9 — Screenshot module: GDI desktop capture into memory stream via GDI+, saved as screenshot.jpg

5.6 PowerShell Loader Execution

Constructs a PowerShell one-liner using iwr / iex to download and execute a secondary payload from C2. Launched via ShellExecuteExA, optionally with the runas verb for elevated execution. The loader retries up to 10 times if execution fails. MSI packages can also be silently installed via msiexec.exe /passive.

Detection note: PowerShell spawned by a non-standard parent (not explorer.exe, not cmd.exe) with -nop -c iex(New-Object Net.WebClient).DownloadString arguments from SysWOW64\... is a high-fidelity alert. Sysmon EID 1, parent process = malware binary.
Figure 10 — PowerShell loader: iex DownloadString one-liner via ShellExecuteExA with optional runas, 10 retry attempts

9. YARA Detection Rule

The rule targets both PE32 (x86) and PE64 (x64) Stealc builds by matching the RC4 initialisation pattern and the Base64-decode call pattern unique to the string decryption routine, combined with the embedded JSON build path or GUID format string.
